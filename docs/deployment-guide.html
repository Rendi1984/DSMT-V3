DSMT - מדריך התקנה והטמעה

Directory Service Management Tool - קונסולת ווב לניהול Active Directory. המדריך מסודר לפי הסדר שבו מבצעים את הפעולות בפועל, מהמכונה הריקה ועד ההתחברות הראשונה ובדיקת הקבלה.

הערת שפה

המדריך בעברית כי הוא תיעוד תפעולי. ממשק הכלי עצמו נשאר אנגלית ו-LTR - זו החלטה מכוונת שמתועדת ב-CLAUDE.md, ואין להכניס מחרוזות עברית לממשק.

לפני שמתחילים: האם יש תהליך התקנה?

אין installer, אין MSI ואין setup.exe. DSMT אינו נארז כחבילת התקנה - הוא אוסף קבצי טקסט שמורצים במקום. "התקנה" כאן היא ארבעה דברים בלבד:

#מה עושיםכמה פעמים
1מתקינים את מודול RSAT ActiveDirectory על המכונהחד-פעמי
2מעתיקים את תיקיית הפרויקט למכונהבכל עדכון גרסה
3מוודאים הרשאות: האצלה ב-AD, גישה ל-SQL, הרשאת האזנה לפורטחד-פעמי
4מריצים Start-DSMT.ps1בכל הפעלה

מה שלא צריך לעשות, ושכדאי לדעת מראש כדי לא לחפש:

  • אין שלב build - אין קומפילציה, אין bundler, אין npm install. שינוי בקובץ הוא חי מיד.
  • אין הורדות בזמן ריצה - אפס בקשות לאינטרנט. הכלי עובד ברשת מנותקת לחלוטין.
  • אין יצירת מסד נתונים ידנית - אם נותנים -SqlServer, המסד והטבלאות נוצרים לבד בהפעלה הראשונה.
  • אין הגדרת משתמשים בכלי - אין מסד משתמשים משלו. מתחברים עם חשבון דומיין, ו-AD קובע מי רשאי לעשות מה.
מצב נוכחי - חשוב

הקוד טרם הורץ מול דומיין חי. הוא נכתב ונבדק סטטית (בדיקות תחביר, איזון סוגריים, סקירת קוד שאיתרה ותיקנה חמישה באגים), אבל ההרצה הראשונה שלך היא גם בדיקת הריצה הראשונה. תכנן אותה כבדיקה בסביבת המעבדה, לא כהטמעת ייצור, ועבור על שלב 9 - בדיקת קבלה במלואו.

שלב 1 - דרישות מוקדמות

שלב 1 מתוך 11

1.1 המכונה שתריץ את הכלי

לא חייב להיות Domain Controller - ועדיף שלא. כל שרת או תחנה שמחוברת לדומיין LAB.LOCAL מתאימה.

דרישהפירוט
מערכת הפעלהWindows Server 2016 ומעלה, או Windows 10/11
PowerShellWindows PowerShell 5.1 (מובנה). לא נדרש PowerShell 7
חברות בדומייןהמכונה חייבת להיות joined ל-LAB.LOCAL
מודול RSATActiveDirectory - מותקן בשלב 2
קישוריותגישה ל-DC (פורטים 389/636/88), וגישה ל-SQL (1433) אם משתמשים בו

1.2 SQL Server - אופציונלי אבל מומלץ

כל מופע נגיש: SQL Server Express, Standard או Enterprise. בלי SQL הכלי עובד במלואו, אבל לוג ה-audit נשמר כקבצי JSONL מקומיים בלבד, ולא נשמרים נתוני מפעילים, סשנים ותצלום הספרייה. המצב הזה מוצג במסך הפתיחה של השרת ובחלון About - כדי שאף אחד לא יניח שיש מסד שמתעד, כשאין.

1.3 דפדפן

Chrome, Edge או Firefox בגרסה עדכנית. הממשק רספונסיבי ממסך טלפון 360px ועד מסך רחב.

שלב 2 - הכנת המכונה

שלב 2 מתוך 11

2.1 התקנת מודול RSAT ActiveDirectory

זו ההתקנה היחידה שהכלי דורש. פתח PowerShell כמנהל:

# Windows Server
Install-WindowsFeature RSAT-AD-PowerShell

# Windows 10 / 11
Add-WindowsCapability -Online -Name Rsat.ActiveDirectory.DS-LDS.Tools~~~~0.0.1.0

2.2 אימות שההתקנה הצליחה

Import-Module ActiveDirectory
Get-ADDomain -Identity LAB.LOCAL | Select-Object DNSRoot, NetBIOSName, DistinguishedName

אם הפקודה מחזירה את פרטי הדומיין - סיימת את השלב. אם היא נכשלת, אין טעם להמשיך: השרת יסרב לעלות בלי זה, ובכוונה.

2.3 מדיניות הרצה

אם ההרצה נחסמת בגלל Execution Policy, ההפעלה שבמדריך כבר עוקפת את זה נקודתית עם -ExecutionPolicy Bypass, בלי לשנות מדיניות גלובלית במכונה.

שלב 3 - העתקת הקבצים

שלב 3 מתוך 11

העתק את תיקיית הפרויקט כמו שהיא, למשל ל-C:\DSMT. המבנה חייב להישמר:

C:\DSMT\
├── Start-DSMT.cmd          ← מפעיל נוח (לערוך ולעשות דאבל-קליק)
├── server\
│   ├── Start-DSMT.ps1      ← נקודת הכניסה
│   └── lib\                ← 6 קבצי הספרייה
├── web\                    ← הממשק (index.html, app.css, app.js)
├── _ds\nocturne-...\       ← ערכת העיצוב
├── uploads\                ← תמונות
├── sql\schema.sql          ← הסכמה, לעיון או ליצירה ידנית
├── data\                   ← נוצר לבד: לוגים ו-audit קבצי
└── docs\                   ← המדריך הזה
אל תפרק את המבנה

Start-DSMT.ps1 מחשב את שורש הפרויקט כתיקיית האב של עצמו, ומגיש ממנה את web\, _ds\ ו-uploads\. העברה של server\ או שינוי שם של web\ שוברים את הנתיבים.

3.1 הרשאות על התיקייה

חשבון ההרצה צריך הרשאת קריאה על כל העץ, והרשאת כתיבה על data\ - שם נכתבים הלוג היומי וקבצי ה-audit.

שלב 4 - חשבון ההרצה והרשאות ב-AD

שלב 4 מתוך 11

4.1 שתי זהויות נפרדות - להבין את ההבחנה

זו הנקודה שהכי מבלבלת בהטמעה, אז כדאי לעצור עליה:

זהותמי זהלמה משמשת
חשבון ההרצה המשתמש שמריץ את Start-DSMT.ps1 איתור DC, קריאה/כתיבה ל-SQL, כתיבה ל-data\
המפעיל מי שמתחבר בדפדפן כל פעולה על הספרייה מתבצעת בהרשאות שלו
המשמעות המעשית

לחשבון ההרצה לא צריכות להיות הרשאות ניהול ב-AD. הוא לא מבצע את הפעולות. כל איפוס סיסמה, unlock, Move OU או מחיקה רץ עם הקרדנשלס של המפעיל שהתחבר - כך שה-DC אוכף את ההרשאות שלו, והשינוי נרשם על שמו בדומיין. ל-DSMT אין מודל הרשאות משלו שיכול לצאת מסנכרון עם המציאות.

4.2 האצלת הרשאות למפעילים

אם מפעיל אמור לאפס סיסמאות - צריך להאציל לו את זה ב-AD, לא בכלי. השתמש ב- Delegation of Control Wizard על ה-OU הרלוונטי, או ב-dsacls. ההרשאות הנפוצות:

פעולה בכליההרשאה הנדרשת ב-AD
Reset passwordReset Password + Write pwdLastSet
UnlockWrite lockoutTime
Enable / DisableWrite userAccountControl
Move OUDelete Child ב-OU המקור + Create Child ב-OU היעד
Add / Remove מקבוצהWrite member על הקבוצה
Create user / groupCreate Child ב-OU היעד
DeleteDelete על האובייקט
"למה אני מקבל Access Denied?"

כי AD דחה את המפעיל, לא כי יש באג. השורה ב-audit תירשם עם תוצאה Denied. התיקון הוא האצלה ב-AD - לא שינוי קוד ב-DSMT.

4.3 עיקרון ההרשאה המזערית

אל תיתן Domain Admins למפעילים כדי "שזה יעבוד". האצל בדיוק את מה שנדרש, ברמת ה-OU. זו בדיוק הסיבה שהכלי בנוי לרוץ בהרשאות המפעיל.

שלב 5 - הכנת SQL Server

שלב 5 מתוך 11

אפשר לדלג על השלב הזה ולהריץ בלי SQL - ראה 1.2. אם כן משתמשים:

5.1 מה נשמר במסד

טבלהתוכן
dbo.Operatorsשורה לכל חשבון שהתחבר לכלי
dbo.Sessionsהיסטוריית סשנים: hash של הטוקן, התחלה, סיום וסיבה
dbo.DirectoryUsersתצלום של אובייקטי המשתמשים שנקראו מ-AD
dbo.DirectoryGroupsתצלום של הקבוצות
dbo.AuditLogכל פעולת כתיבה שנוסתה, כולל כישלונות
טבלאות התצלום אינן מקור האמת

DirectoryUsers ו-DirectoryGroups נכתבות אחרי קריאה חיה מ-AD, ומתיישנות ברגע שהספרייה משתנה. הקונסולה תמיד מציגה קריאה חיה. השתמש בטבלאות האלה לדוחות והיסטוריה - לעולם לא כדי לענות על "איך הספרייה נראית עכשיו".

5.2 מה לא נשמר

שום סיסמה לא נכתבת למסד. לא של מפעילים ולא של משתמשי קצה. dbo.Sessions שומרת SHA-256 של הטוקן בלבד, כך שאין בו שום דבר שניתן לשחזור או להשמעה חוזרת.

5.3 הרשאות SQL

ברירת המחדל היא Windows Authentication - כלומר חשבון ההרצה ניגש ל-SQL. שתי אפשרויות:

אפשרות א' - שהכלי ייצור את המסד (הפשוטה)

נדרשת הרשאת dbcreator על המופע, פעם אחת:

USE master;
CREATE LOGIN [LAB\svc-dsmt] FROM WINDOWS;
ALTER SERVER ROLE dbcreator ADD MEMBER [LAB\svc-dsmt];

אפשרות ב' - ליצור את המסד מראש (המסודרת)

ה-DBA יוצר את המסד ומריץ את הסכמה, והכלי רק כותב אליה:

sqlcmd -S SQL01 -Q "CREATE DATABASE [DSMT];"
sqlcmd -S SQL01 -d DSMT -i C:\DSMT\sql\schema.sql
USE DSMT;
CREATE USER [LAB\svc-dsmt] FOR LOGIN [LAB\svc-dsmt];
ALTER ROLE db_datareader ADD MEMBER [LAB\svc-dsmt];
ALTER ROLE db_datawriter ADD MEMBER [LAB\svc-dsmt];

בשתי האפשרויות, בכל הפעלה הכלי בודק אילו טבלאות חסרות ויוצר אותן - הפעולה בטוחה לחזרה ולא נוגעת בטבלאות קיימות.

שלב 7 - הרצה ראשונה

שלב 7 מתוך 11

7.1 הפעלה

ההרצה המלאה, כפי שתיראה במעבדה:

cd C:\DSMT
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\server\Start-DSMT.ps1 `
    -Domain LAB.LOCAL -ListenAddress any -Port 8080 `
    -SqlServer SQL01 -SqlDatabase DSMT

הרצה מינימלית לבדיקה ראשונה - מקומית בלבד, בלי SQL:

powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\server\Start-DSMT.ps1

לחלופין: ערוך את המשתנים בראש Start-DSMT.cmd (DSMT_DOMAIN, DSMT_PORT, DSMT_SQLSERVER) ועשה דאבל-קליק.

7.2 קריאת מסך הבדיקות

לפני שהוא מאזין, השרת מריץ בדיקות מקדימות ומדפיס את התוצאה:

  DSMT - Directory Service Management Tool
  Version <the version from DsmtCommon.ps1>

  [ok]   ActiveDirectory module loaded
  [ok]   Domain lab.local reachable (LAB)
  [ok]   SQL Server SQL01 - database [DSMT] ready
  [ok]   Front end found

  Listening on http://+:8080/
  Open http://localhost:8080/
  Managing LAB.LOCAL - operators sign in with their own domain account
  Audit log: C:\DSMT\data
  Ctrl+C to stop.
כישלון בבדיקה מקדימה עוצר את השרת בכוונה

כל בדיקה שנכשלת מדפיסה את התיקון שלה ומפילה את התהליך. זה מכוון: תקלת סביבה שנבלעת עכשיו תחזור מאוחר יותר כשגיאה שנראית כמו באג בקוד, ותבזבז מחזור אבחון שלם.

אם אין SQL, תופיע שורת אזהרה במקום השורה הירוקה - וזה תקין:

  [warn] No -SqlServer given: operators, sessions and the directory snapshot are NOT stored,
         and the audit log is written to JSONL files in C:\DSMT\data

שלב 8 - החיבור הראשוני

שלב 8 מתוך 11

8.1 איך מתחברים

1. פתח בדפדפן:

http://localhost:8080/          מהמכונה עצמה
http://dsmt-srv.lab.local:8080/ ממכונה אחרת ברשת

2. יופיע מסך ההתחברות. בפינה התחתונה מוצג באדג' עם מספר הגרסה - הוא נקרא מהשרת, ומאשר שהדפדפן מדבר עם ה-API בהצלחה. אם הבאדג' ריק, הדף נטען אבל ה-API לא עונה.

3. הזן חשבון דומיין. כל אחד מהפורמטים הבאים תקין:

LAB\jdoe
jdoe@lab.local
jdoe

4. לחץ Sign in, או פשוט הקש Enter בשדה שם המשתמש או הסיסמה - שניהם שולחים את הטופס.

במי להשתמש בהתחברות הראשונה

השתמש בחשבון שכבר מוגדרות לו ההרשאות משלב 4. אין "חשבון ברירת מחדל", אין admin/admin ואין אשף יצירת משתמש ראשון - לכלי אין מסד משתמשים משלו כלל. כל מי שיש לו חשבון תקין בדומיין יכול להיכנס ולצפות; מה שהוא יוכל לשנות נקבע לגמרי על ידי ההאצלות שלו ב-AD.

8.2 מה קורה מאחורי הקלעים

  1. הדפדפן שולח POST /api/session עם שם המשתמש והסיסמה.
  2. השרת מאמת אותם מול הדומיין (PrincipalContext.ValidateCredentials).
  3. בהצלחה - נוצר טוקן סשן, והקרדנשלס נשמרים בזיכרון התהליך בלבד כדי שאפשר יהיה לבצע פעולות בשם המפעיל.
  4. נרשמת שורת audit של Sign in; אם SQL מוגדר, נרשמים גם המפעיל והסשן.
  5. הטוקן נשמר ב-localStorage בדפדפן, והממשק נטען.

גם התחברות שנכשלה נרשמת ב-audit עם תוצאה Denied - כך שניסיונות כושלים נראים בלוג.

8.3 רענון הדף (F5) לא מנתק

הטוקן נשמר ב-localStorage ומאומת מול השרת בכל טעינת דף, כך שרענון, סגירת טאב או פתיחה מחדש של הדפדפן אינם מבקשים סיסמה שוב. הסשן פג אחרי 8 שעות של חוסר פעילות (ניתן לשינוי עם -SessionHours).

מה כן מנתק את כולם

הפעלה מחדש של השרת. הקרדנשלס שנדרשים לפעולות מול AD קיימים רק בזיכרון ולא נשמרים לשום מקום - ובמכוון. אחרי ריסטארט כל המפעילים יתחברו מחדש. זה לא באג.

8.4 ההתמצאות הראשונה בממשק

איפהמה זה
כותרת עליונהשם הדומיין ומספר ה-DC-ים האמיתי, נקרא חי
טאבים Users / Groupsרשימות חיות מהספרייה. החיפוש רץ מול AD, לא מסנן טבלה טעונה
כפתור Aboutגרסה, דומיין, יער, רשימת ה-DC-ים, ואיפה נשמרות הרשומות
תפריט (☰)ניווט, About, רענון מהספרייה, והתנתקות
Audit logכל פעולת כתיבה שבוצעה דרך הכלי

שלב 9 - בדיקת קבלה

שלב 9 מתוך 11

עבור על הרשימה לפי הסדר. אל תדלג - זו ההרצה הראשונה של הקוד מול דומיין חי. בצע אותה על חשבון בדיקה, לא על חשבון אמיתי.

  • מסך ההתחברות נטען ומספר הגרסה מופיע בתחתית
  • התחברות עם חשבון דומיין מצליחה; אנטר בשדה הסיסמה עובד
  • בכותרת מופיעים שם הדומיין ומספר DC-ים נכון
  • About מציג את הגרסה, את היער ואת רשימת ה-DC-ים; ושורת "Record store" תואמת למה שהגדרת (SQL או קבצים)
  • טאב Users מציג משתמשים אמיתיים מ-LAB.LOCAL
  • חיפוש לפי שם, לפי מחלקה ולפי UPN מחזיר תוצאות סבירות ובמהירות מקובלת
  • לחיצה על שורה פותחת חלונית פרטים עם חברויות בקבוצות אמיתיות
  • טאב Groups מציג קבוצות אמיתיות עם מספר חברים נכון
  • איפוס סיסמה על חשבון בדיקה מצליח, והסיסמה שנוצרה מוצגת פעם אחת
  • ניסיון לשמור בלי סיבה נחסם - כפתור האישור לא מבצע
  • הפעולה מופיעה ב-Audit log עם המפעיל, ה-DC, הסיבה ותוצאה Success
  • אם SQL מוגדר: SELECT TOP 10 * FROM dbo.AuditLog ORDER BY TimeUtc DESC מחזיר את אותה שורה
  • ייצוא CSV מוריד קובץ ונפתח נכון באקסל
  • פעולה מרובה על 2-3 חשבונות בדיקה מדווחת תוצאה לכל יעד בנפרד
  • F5 באמצע העבודה לא מבקש התחברות מחדש
  • פתיחה בטלפון: הטבלה נפרסת לכרטיסים וכל הנתונים נגישים
נקודות שכדאי לשים לב אליהן במיוחד בהרצה הראשונה

שם ה-DC בשורות ה-audit צריך להיראות כמו שרת אחד ולא שניים מודבקים; Set-ADAccountPassword עובד מול ערוץ Negotiate מוצפן ללא LDAPS - אם הוא נכשל, החשודים הרגילים הם מדיניות סיסמאות או האצלת Reset Password חסרה; וכדאי לבדוק אם מגבלת 500 התוצאות מתאימה לגודל המעבדה שלך (-PageSize).

שלב 10 - HTTPS לפני ייצור

שלב 10 מתוך 11
אל תפעיל ברשת מעבר ל-HTTP

בהתחברות נשלחים שם משתמש וסיסמה של דומיין. מעל HTTP הם עוברים ברשת בלי הצפנה. עבור מעבדה מקומית זה סביר; לפני כל שימוש אמיתי - חובה HTTPS.

1. ייבא תעודת שרת ל-LocalMachine\My וקח את ה-thumbprint.

2. קשור אותה לפורט:

netsh http add sslcert ipport=0.0.0.0:8443 certhash=<THUMBPRINT> `
    appid={00000000-0000-0000-0000-000000000000}

3. ב-server\Start-DSMT.ps1 שנה את בניית הכתובת מ-http:// ל-https://.

4. הפעל עם -Port 8443.

שלב 11 - הרצה קבועה כשירות

שלב 11 מתוך 11

השרת רץ בחלון PowerShell פתוח. להרצה מתמדת, ההמלצה הפשוטה היא Scheduled Task שרץ תחת חשבון השירות, מופעל באתחול המכונה: 

$action = New-ScheduledTaskAction -Execute "powershell.exe" `
    -Argument "-NoProfile -ExecutionPolicy Bypass -File C:\DSMT\server\Start-DSMT.ps1 -Domain LAB.LOCAL -ListenAddress any -SqlServer SQL01"

$trigger = New-ScheduledTaskTrigger -AtStartup

Register-ScheduledTask -TaskName "DSMT Console" -Action $action -Trigger $trigger `
    -User "LAB\svc-dsmt" -RunLevel Limited

שים לב שנדרשת הזמנת ה-URL משלב 6.2 כדי שזה יעבוד ללא הרשאות מוגברות.

ב. פורמט קובץ ה-CSV לייבוא מרובה

שורת כותרות חובה. העמודה היחידה שחובה למלא היא SamAccountName:

SamAccountName,DisplayName,GivenName,Surname,Department,Title,Password,OU
jdoe,John Doe,John,Doe,IT,Helpdesk,,
asmith,Anna Smith,Anna,Smith,Finance,Analyst,,OU=Finance,DC=lab,DC=local
  • שורה בלי Password מקבלת סיסמה אקראית תקנית.
  • שורה בלי OU משתמשת ב-OU שנבחר בחלון הייבוא.
  • כל שורה מדווחת בנפרד; כישלון בשורה אחת לא עוצר את השאר.
  • כל שורה נרשמת ב-audit בנפרד.

ג. מודל האבטחה - תקציר

  • אין מסד משתמשים בכלי. אימות מול הדומיין בלבד.
  • כל פעולה רצה בהרשאות המפעיל; AD אוכף, ו-AD מתעד.
  • הסיסמה נשמרת בזיכרון התהליך למשך הסשן - ולכן השרת חייב לרוץ על מכונה מוגבלת ומאחורי HTTPS.
  • סיסמאות לא נכתבות ל-SQL, ל-audit או ללוג. במסד יש רק hash של הטוקן.
  • קלט חיפוש עובר escaping לפני שהוא נכנס למסנן LDAP; כל שאילתות ה-SQL פרמטריות.
  • סיבה היא שדה חובה בכל כתיבה, ונשמרת ברשומת ה-audit.
שיפור עתידי שנבחן ונדחה במודע

Kerberos Constrained Delegation היה מייתר את החזקת הסיסמה בזיכרון. הוא נדחה כרגע כי הוא דורש הגדרת SPN והאצלה מול הדומיין החי - דבר שאי אפשר לתכנן "על היבש". התיעוד המלא ב-CLAUDE.md תחת "Attempted and deliberately NOT pursued". לפני שמישהו מתחיל את זה מחדש - צריך לתאם.
