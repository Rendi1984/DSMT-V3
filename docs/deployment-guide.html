DSMT - Deployment Guide

Directory Service Management Tool - a web console for Active Directory operations. This guide is ordered the way the work is actually done: from a bare machine, through the first connection, to the acceptance test.

Before you start: is there an install process?

There is no MSI and no setup.exe - DSMT is not packaged as a Windows installer. But there is an install script that does everything automatically: Install-DSMT.ps1 (or Install-DSMT.cmd for a double-click). It installs the RSAT module, prepares the folders, creates the database, reserves the port, opens the firewall and saves the settings. See the fast path.

What "installing" actually consists of is four things:

#WhatHow oftenAutomated?
1Copy the project folder to the machineEvery version updateManual
2Run Install-DSMT.ps1: RSAT, folders, database, port, firewallOnceAutomated
3Delegate rights to the operators in ADOnceManual - step 4
4Run Start-DSMT.ps1Every startOr as a scheduled task

What you do not need to do, worth knowing so you do not go looking:

  • No build step - no compilation, no bundler, no npm install. A changed file is live immediately.
  • No runtime downloads - zero requests to the internet. The tool works on a fully disconnected network.
  • No manual database creation - given -SqlServer, the database and tables are created on first start.
  • No user setup inside the tool - there is no user store of its own. You sign in with a domain account, and AD decides what you may do.
Current status - important

The code has not yet been run against a live domain. It was written and verified statically (syntax checks, brace balance, a code review that found and fixed five defects), but your first run is also its first execution. Plan it as a test in the lab, not as a production rollout, and work through step 9 - acceptance test in full.

The fast path - the automated installer

Install-DSMT.ps1 performs every preparation step described in the rest of this guide. This is the recommended path. Manual steps 1-11 remain here as documentation of what happens under the hood, and for cases where something has to be done separately.

How to run it

Option A - double-click:

  1. Edit the variables at the top of Install-DSMT.cmd (domain, port, service account, SQL server).
  2. Run the file. The script requests elevation itself and opens an elevated window.

Option B - command line:

# Full lab setup, including start at boot
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\server\Install-DSMT.ps1 `
    -Domain LAB.LOCAL -SqlServer SQL01 -ServiceAccount "LAB\svc-dsmt" -InstallScheduledTask

# Minimal - finds a local SQL instance if there is one
.\server\Install-DSMT.ps1

# No database at all
.\server\Install-DSMT.ps1 -SkipSql
Safe to re-run

Every step checks the current state first and does nothing if the machine is already correct. If something fails, fix it and run the same command again.

What it does, step by step

The saved settings file

After installation, Start-DSMT.ps1 reads config\dsmt.config.json and uses the stored values. That means the console can be started with no parameters at all: 

.\server\Start-DSMT.ps1

A parameter passed explicitly on the command line always wins over the saved file, so you can deviate for one run without editing it. The startup banner states that settings came from the file, and when it was installed.

Expected output

  2. Windows PowerShell version
       [ok]   PowerShell 5.1.17763.5576
  3. Domain membership
       [ok]   Joined to lab.local

If something fails, the summary lists exactly what is left and what to do about it - rather than leaving you to discover it on the first run.

What it cannot do on its own

Three things the script deliberately does not do, and why:

WhatWhy notWhat to do instead
Download RSAT from the internet on a disconnected Windows 10/11 client Add-WindowsCapability fetches the component from Windows Update; on a disconnected network there is no source Run with -FeatureSource pointing at Feature-on-Demand media or \sources\sxs from an ISO
Download SQL Server Express DSMT hosts usually sit on a network with no internet route, and a silent download would contradict the tool's disconnected-by-design principle If there is no SQL instance: fetch the media in advance and run with -SqlExpressSetup <path> - the install itself then runs unattended. Or simply -SkipSql
Delegate rights to operators in AD A security decision that depends on your OU structure and organisational policy - not something an install script should decide Step 4.2 - delegate exactly what is needed, at OU level
AD delegation is still manual work

The script prepares the machine, not the domain. Even after a perfect install, an operator without Reset Password delegation will simply get Denied - and that is correct behaviour. Work through step 4.

Once the script finishes successfully you can skip straight to step 7 - first run. If you would rather understand or perform each step yourself, keep reading in order.

Step 1 - Prerequisites

STEP 1 OF 11

1.1 The machine that will run the tool

It does not have to be a domain controller - and preferably is not. Any server or workstation joined to LAB.LOCAL will do.

RequirementDetail
Operating systemWindows Server 2016 or later, or Windows 10/11
PowerShellWindows PowerShell 5.1 (built in). PowerShell 7 is not required
Domain membershipThe machine must be joined to LAB.LOCAL
RSAT moduleActiveDirectory - installed in step 2
ConnectivityAccess to a DC (ports 389/636/88), and to SQL (1433) if used

1.2 SQL Server - optional but recommended

Any reachable instance: SQL Server Express, Standard or Enterprise. Without SQL the tool works in full, but the audit log is written only to local JSONL files, and operators, sessions and the directory snapshot are not stored at all. That state is reported in the server's startup banner and in the About dialog - so nobody assumes a database is recording things when it is not.

1.3 Browser

A current Chrome, Edge or Firefox. The interface is responsive from a 360px phone to an ultrawide monitor.

Step 2 - Prepare the machine

STEP 2 OF 11
The installer does this entire step for you

Install-DSMT.ps1 detects whether this is a server or a client, installs the right component and verifies that the domain answers. The detail here is for doing it by hand, or for understanding what happens.

2.1 Install the RSAT ActiveDirectory module

This is the only install the tool requires. Open PowerShell as administrator:

# Windows Server
Install-WindowsFeature RSAT-AD-PowerShell

# Windows 10 / 11
Add-WindowsCapability -Online -Name Rsat.ActiveDirectory.DS-LDS.Tools~~~~0.0.1.0

2.2 Verify the install worked

Import-Module ActiveDirectory
Get-ADDomain -Identity LAB.LOCAL | Select-Object DNSRoot, NetBIOSName, DistinguishedName

If that returns the domain details, the step is done. If it fails there is no point continuing: the server refuses to start without it, by design.

2.3 Execution policy

If execution is blocked by the execution policy, the launch commands in this guide already work around it locally with -ExecutionPolicy Bypass, without changing machine-wide policy.

Step 3 - Copy the files

STEP 3 OF 11

Copy the project folder as it is, for example to C:\DSMT. The structure must be preserved:

C:\DSMT\
├── Install-DSMT.cmd        ← the automated installer
├── Start-DSMT.cmd          ← convenience launcher
├── server\
│   ├── Install-DSMT.ps1
│   ├── Start-DSMT.ps1      ← the entry point
│   └── lib\                ← the six library files
├── web\                    ← the front end (index.html, app.css, app.js)
├── _ds\nocturne-...\       ← the design system
├── uploads\                ← images
├── sql\schema.sql          ← the schema, for review or manual creation
├── config\                 ← created by the installer: saved settings
├── data\                   ← created automatically: logs and file audit
└── docs\                   ← this guide
Do not break the layout

Start-DSMT.ps1 resolves the project root as its own parent directory and serves web\, _ds\ and uploads\ from there. Moving server\ or renaming web\ breaks those paths.

3.1 Folder permissions

The run account needs read access to the whole tree, and write access to data\ - that is where the daily log and the audit files are written.

Step 4 - Run account and AD delegation

STEP 4 OF 11

4.1 Two separate identities - understand the distinction

This is the part of a rollout that confuses people most, so it is worth pausing here:

IdentityWho it isWhat it is used for
The run account The user that runs Start-DSMT.ps1 Locating a DC, reading/writing SQL, writing to data\
The operator Whoever signs in through the browser Every directory operation runs with their rights
What this means in practice

The run account does not need AD administrative rights. It is not the account performing the operations. Every password reset, unlock, OU move or deletion runs with the credentials of the signed-in operator - so the DC enforces their rights, and the change is attributed to their account in the domain. DSMT has no permission model of its own that could drift out of step with reality.

4.2 Delegating rights to operators

If an operator is meant to reset passwords, that has to be delegated in AD, not in the tool. Use the Delegation of Control Wizard on the relevant OU, or dsacls. The common permissions:

Action in the toolRights required in AD
Reset passwordReset Password + Write pwdLastSet
UnlockWrite lockoutTime
Enable / DisableWrite userAccountControl
Move OUDelete Child on the source OU + Create Child on the target OU
Add / Remove group memberWrite member on the group
Create user / groupCreate Child on the target OU
DeleteDelete on the object
"Why am I getting Access Denied?"

Because AD rejected the operator, not because there is a bug. The audit row is recorded with result Denied. The fix is delegation in AD - not a code change in DSMT.

4.3 Least privilege

Do not hand out Domain Admins to make things work. Delegate exactly what is needed, at OU level. That is precisely why the tool is built to run with the operator's own rights.

Step 5 - Prepare SQL Server

STEP 5 OF 11
The installer creates the database for you

Install-DSMT.ps1 finds a local SQL instance, creates the database and all its tables, and verifies they exist. The only manual part left is granting SQL permissions (5.3), and only if the run account is not already authorised.

You can skip this step entirely and run without SQL - see 1.2 - and add it later from Menu → Settings in the console itself, without restarting. If you do use it:

5.1 What is stored

TableContents
dbo.OperatorsOne row per account that has signed in to the tool
dbo.SessionsSession history: token hash, start, end and reason
dbo.DirectoryUsersSnapshot of the user objects read from AD
dbo.DirectoryGroupsSnapshot of the groups
dbo.AuditLogEvery write that was attempted, failures included
The snapshot tables are not the source of truth

DirectoryUsers and DirectoryGroups are written after a live read from AD, and go stale the moment the directory changes. The console always displays a live read. Use these tables for reporting and history - never to answer "what does the directory look like right now".

5.2 What is not stored

No password is ever written to the database - neither operators' nor end users'. dbo.Sessions holds only a SHA-256 hash of the session token, so there is nothing in it that can be recovered or replayed.

5.3 SQL permissions

The default is Windows authentication, meaning the run account connects to SQL. Two options:

Option A - let the tool create the database (simplest)

Requires dbcreator on the instance, once:

USE master;
CREATE LOGIN [LAB\svc-dsmt] FROM WINDOWS;
ALTER SERVER ROLE dbcreator ADD MEMBER [LAB\svc-dsmt];

Option B - create the database up front (tidiest)

The DBA creates the database and runs the schema; the tool only writes to it:

sqlcmd -S SQL01 -Q "CREATE DATABASE [DSMT];"
sqlcmd -S SQL01 -d DSMT -i C:\DSMT\sql\schema.sql
USE DSMT;
CREATE USER [LAB\svc-dsmt] FOR LOGIN [LAB\svc-dsmt];
ALTER ROLE db_datareader ADD MEMBER [LAB\svc-dsmt];
ALTER ROLE db_datawriter ADD MEMBER [LAB\svc-dsmt];

Either way, on every start the tool checks which tables are missing and creates them - an operation that is safe to repeat and does not touch existing tables.

Step 6 - Network, port and listener reservation

STEP 6 OF 11
The installer does this entire step for you

The URL reservation and the firewall rule are handled automatically when -ListenAddress any.

6.1 The two listen modes

ValueWho can reach itRequirements
-ListenAddress localhost (default)Only this machineNone. Works immediately
-ListenAddress anyAny machine on the networkA reservation - see 6.2

6.2 Reserving the URL for all interfaces

Listening on all interfaces requires permission. Either run from an elevated PowerShell, or - better - make a one-time URL reservation that lets it run without elevated rights: 

netsh http add urlacl url=http://+:8080/ user="LAB\svc-dsmt"

6.3 Firewall

New-NetFirewallRule -DisplayName "DSMT console" -Direction Inbound `
    -Protocol TCP -LocalPort 8080 -Action Allow

Step 7 - First run

STEP 7 OF 11

7.1 Starting it

After running the installer, no parameters are needed:

cd C:\DSMT
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\server\Start-DSMT.ps1

Without the installer, or to override the saved settings:

powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\server\Start-DSMT.ps1 `
    -Domain LAB.LOCAL -ListenAddress any -Port 8080 `
    -SqlServer SQL01 -SqlDatabase DSMT

Alternatively: edit the variables at the top of Start-DSMT.cmd (DSMT_DOMAIN, DSMT_PORT, DSMT_SQLSERVER) and double-click it.

7.2 Reading the preflight banner

Before it listens, the server runs preflight checks and prints the result:

  DSMT - Directory Service Management Tool
  Version <the version from DsmtCommon.ps1>

  [ok]   ActiveDirectory module loaded
  [ok]   Domain lab.local reachable (LAB)
  [ok]   SQL Server SQL01 - database [DSMT] ready
  [ok]   Front end found

  Listening on http://+:8080/
  Open http://localhost:8080/
  Managing LAB.LOCAL - operators sign in with their own domain account
  Audit log: C:\DSMT\data
  Ctrl+C to stop.
A failed preflight check stops the server on purpose

Every failing check prints its own fix and terminates the process. That is deliberate: an environment problem swallowed now comes back later as an error that looks like a code bug, and costs a whole diagnostic cycle.

Without SQL, a warning line appears instead of the green one - and that is correct:

  [warn] No -SqlServer given: operators, sessions and the directory snapshot are NOT stored,
         and the audit log is written to JSONL files in C:\DSMT\data

Step 8 - The first connection

STEP 8 OF 11

8.1 How to sign in

1. Open a browser:

http://localhost:8080/          from the machine itself
http://dsmt-srv.lab.local:8080/ from another machine on the network

2. The sign-in screen appears. A badge in the bottom corner shows the version number - it is read from the server, and confirms the browser is talking to the API successfully. If the badge is empty, the page loaded but the API is not answering.

3. Enter a domain account. Any of these formats is accepted:

LAB\jdoe
jdoe@lab.local
jdoe

4. Click Sign in, or simply press Enter in either the username or the password field - both submit the form.

Which account to use for the first connection

Use an account that already has the rights from step 4. There is no "default account", no admin/admin and no first-user wizard - the tool has no user store of its own at all. Anyone with a valid domain account can sign in and browse; what they can change is decided entirely by their delegation in AD.

8.2 What happens behind the scenes

  1. The browser sends POST /api/session with the username and password.
  2. The server validates them against the domain (PrincipalContext.ValidateCredentials).
  3. On success a session token is created, and the credentials are held in process memory only so operations can be performed as that operator.
  4. A Sign in audit row is written; if SQL is configured, the operator and the session are recorded too.
  5. The token is stored in localStorage in the browser and the console loads.

Failed sign-ins are audited too, with result Denied - so unsuccessful attempts are visible in the log.

8.3 Refreshing the page (F5) does not sign you out

The token is kept in localStorage and revalidated against the server on every page load, so a refresh, closing a tab, or reopening the browser does not ask for the password again. The session expires after 8 hours of inactivity (configurable with -SessionHours).

What does sign everyone out

Restarting the server. The credentials needed for AD operations exist only in memory and are never persisted - by design. After a restart, all operators sign in again. This is not a bug.

8.4 Finding your way around

WhereWhat it is
HeaderThe real domain name, detected automatically
Users / Groups tabsLive lists from the directory. Search runs against AD, it does not filter a preloaded table
Bell iconNotifications raised from real server state - for example, that no SQL database is configured, with a button to create one
About buttonVersion, domain, forest, DC list, and where records are stored
Menu (three lines)Navigation, Settings, About, refresh from the directory, and sign out
Audit logEvery write performed through the tool, filterable by category and by date range

8.5 Creating the database from the console

If DSMT was started without SQL, the bell shows a notification saying so. Menu → Settings lets you enter a SQL Server instance and create the DSMT database and its tables without restarting the server. The setting is saved to config\dsmt.config.json, so it survives a restart, and the change is written to the audit log.

Creating a database needs the dbcreator right on the instance; connecting to one that already exists needs only read and write. See step 5.3.

8.6 Filtering the audit log by date

The audit view has two rows of filter chips. The first selects a time window - Last 24 hours, Last 48 hours, Last 7 days, Last 30 days, All time, or Custom range with two date/time pickers. The second filters by category (Users, Groups, Passwords, Deletions). Both combine with the free-text search box.

Ranges are evaluated in your own timezone and applied inside the SQL query, so the result count is the true number of records in that window - not the most recent few hundred filtered afterwards. The line under the table always names the window it counted and whether the records came from SQL Server or from the file log.

Step 9 - Acceptance test

STEP 9 OF 11

Work through the list in order. Do not skip it - this is the first execution of the code against a live domain. Run it against a test account, not a real one.

  • The sign-in screen loads and the version number appears at the bottom
  • Signing in with a domain account works; Enter in the password field submits
  • The header shows the correct domain name and DC count
  • About shows the version, the forest and the DC list; and the "Record store" line matches what you configured (SQL or files)
  • The Users tab shows real users from LAB.LOCAL
  • Searching by name, by department and by UPN returns sensible results at an acceptable speed
  • Clicking a row opens the detail pane with real group memberships
  • The Groups tab shows real groups with correct member counts
  • Resetting the password of a test account succeeds, and the generated password is shown once
  • Attempting to save without a reason is blocked - the confirm button does nothing
  • The action appears in the Audit log with the operator, the DC, the reason and result Success
  • If SQL is configured: SELECT TOP 10 * FROM dbo.AuditLog ORDER BY TimeUtc DESC returns that same row
  • The audit range chips work: Last 24 hours and Last 48 hours narrow the list, and a custom range returns what you expect for a known date
  • If you started without SQL: the bell shows the "no database configured" notification, and Settings creates the database successfully
  • CSV export downloads a file that opens correctly in Excel
  • A bulk action on 2-3 test accounts reports a result per target
  • Pressing F5 mid-session does not ask you to sign in again
  • On a phone: the table reflows into cards and all the data is reachable
Things worth watching specifically on the first run

The DC name in the audit rows should look like one server, not two concatenated; Set-ADAccountPassword works over an encrypted Negotiate channel without LDAPS - if it fails, the usual suspects are password policy or missing Reset Password delegation; and check whether the 500-result cap suits the size of your lab (-PageSize).

Step 10 - HTTPS before production

STEP 10 OF 11
Do not expose it over HTTP on a network

Signing in sends a domain username and password. Over HTTP they cross the network unencrypted. For a local lab that is tolerable; before any real use, HTTPS is mandatory.

1. Import a server certificate into LocalMachine\My and note its thumbprint.

2. Bind it to the port:

netsh http add sslcert ipport=0.0.0.0:8443 certhash=<THUMBPRINT> `
    appid={00000000-0000-0000-0000-000000000000}

3. In server\Start-DSMT.ps1, change the prefix from http:// to https://.

4. Start with -Port 8443.

Step 11 - Running permanently

STEP 11 OF 11

Run by hand, the server lives in an open PowerShell window and dies with it. For permanent operation there are two supported options. The installer sets up either one.

11.1 Choosing between them

Scheduled taskWindows service
Installer switch-InstallScheduledTask-InstallAsService
In Install-DSMT.cmdset DSMT_AUTOSTART=1set DSMT_SERVICE=1
Starts at bootYesYes
Restarts on failureYes (3 attempts, 1 min apart)Yes (5s, 10s, then every 30s)
Managed withGet-ScheduledTask "DSMT Console"Get-Service DSMT
Extra moving partsNoneA compiled host executable

Recommendation: the scheduled task, unless you specifically need service semantics. It uses nothing but what Windows already ships and has nothing to go stale. Choose the service if your operations processes are built around Get-Service / Restart-Service, or if you want the service manager's recovery behaviour.

11.2 As a Windows service

.\server\Install-DSMT.ps1 -Domain LAB.LOCAL -SqlServer SQL01 `
    -ServiceAccount "LAB\svc-dsmt" -InstallAsService -StartWhenDone
Why there is a compiled host

PowerShell cannot be a Windows service directly - the service control manager terminates any process that does not answer its protocol within the start timeout. Pointing New-Service at powershell.exe looks like it should work and does not; it is a common trap. The installer therefore compiles a small C# host, server\DsmtService.exe, using the csc.exe that ships with the .NET Framework - nothing is downloaded - and that host runs Start-DSMT.ps1 as a child process. If the console dies, the host reports failure so the service manager restarts it rather than leaving a service that claims to be running with nothing behind it.

With -ServiceAccount you are prompted for that account's password, because the service control manager has to store it. Without it the service runs as LocalSystem, reaching AD and SQL as the computer account - in which case grant LAB\SERVERNAME$ rights on the SQL instance. 

Get-Service DSMT
Restart-Service DSMT
Stop-Service DSMT

11.3 As a scheduled task

.\server\Install-DSMT.ps1 -Domain LAB.LOCAL -SqlServer SQL01 `
    -ServiceAccount "LAB\svc-dsmt" -InstallScheduledTask -StartWhenDone

The installer configures three things that a hand-made task usually misses:

  • No execution time limit - the default stops a task after 72 hours, which would take the console down every three days.
  • Restart on failure - three attempts, a minute apart.
  • Runs whether or not anyone is signed in, and starts even if the machine was unavailable at the scheduled moment.

To register it by hand instead:

$action = New-ScheduledTaskAction -Execute "powershell.exe" `
    -Argument "-NoProfile -ExecutionPolicy Bypass -File C:\DSMT\server\Start-DSMT.ps1"

$trigger = New-ScheduledTaskTrigger -AtStartup

$settings = New-ScheduledTaskSettingsSet -RestartCount 3 `
    -RestartInterval (New-TimeSpan -Minutes 1) `
    -ExecutionTimeLimit ([TimeSpan]::Zero) -StartWhenAvailable

Register-ScheduledTask -TaskName "DSMT Console" -Action $action -Trigger $trigger `
    -Settings $settings -User "LAB\svc-dsmt" -RunLevel Limited
Both options need the URL reservation

Step 6.2 is what lets DSMT listen without elevated rights. Without it, an unprivileged service or task fails to start with "Could not listen on http://+:8080/".

11.4 Diagnosing a start that fails with no console

Under a service or a task there is no window to read the preflight banner in. Every startup failure is therefore also written to data\dsmt-YYYY-MM-DD.log - check there first, before anything else.

The version number

The version is defined in exactly one place: $script:DsmtVersion in server\lib\DsmtCommon.ps1. From there it reaches the sign-in screen, the About dialog, the server's startup banner, the log lines and the audit records. Never type a version number anywhere else - that is precisely the failure this rule prevents. Format: MAJOR.FEATURE.FIX.

D. Security model - summary

  • There is no user store in the tool. Authentication is against the domain only.
  • Every operation runs with the operator's rights; AD enforces, and AD records.
  • The password is held in process memory for the session lifetime - which is why the server must run on a restricted machine and behind HTTPS.
  • Passwords are never written to SQL, to the audit log or to the log file. The database holds only a token hash.
  • Search input is escaped before it enters an LDAP filter; every SQL statement is parameterised.
  • A reason is mandatory on every write and is stored on the audit record.
A future improvement, deliberately deferred

Kerberos constrained delegation would remove the need to hold the password in memory. It is deferred for now because it requires SPN registration and delegation configuration against the live domain - something that cannot be designed blind. Full record in CLAUDE.md under "Attempted and deliberately NOT pursued". Check in before anyone restarts that investigation.

Final warning: prototype\

The prototype\ folder holds the original mock-up. Every row in it is invented and every button is inert. It is very convincing, and therefore dangerous - do not demo it to anyone who might believe the rows are real, and do not use it to check whether a feature works.
